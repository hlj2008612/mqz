# 架构与设计决策

## 照片墙渲染引擎（src/core/）

### 世界坐标系

- `WORLD_COLS=20` × `WORLD_ROWS=15` = 300 个槽位
- `STEP=340`，世界尺寸 `WORLD_W=6800` × `WORLD_H=5100`
- 20 张图在 300 个槽位里**循环复用**，每张图被 15 个槽位共用
- 图片分配公式：`imageIndexAt(col, row) = ((col*47 + row*31) % 20 + 20) % 20 + 1`

### 核心设计：可见性过滤与定位合并

**旧实现（已废弃）**有两个独立计算互相矛盾：可见性过滤用滚动原点算，定位却用屏幕中心重新找最近格子，
导致约 23% 通过过滤的卡片实际被放到视口外，白白付出 10 次 k 循环 + 样式写入。

**现实现**：直接用取模数学一次算出每张卡的屏幕位置，不再做 k=-2..2 的循环搜索。
`cellX = (wrappedCol + WORLD_COLS*m) * currentStep - scrollX` —— 注意 **scrollX 是摄像机左边界**，
scrollX 增大 = 摄像机右移 = 内容在屏幕上向左移动。

### 渲染循环的关键优化

- **样式差分写入**：只有几何真的变了才写 style，静止帧写入次数 = **0**（旧版 450~600）
- **卡片延迟回收**：离开视口 4 秒后才 detach，避免频繁进出时反复创建
- **零布局读取**：渲染路径中不调 `getBoundingClientRect`，尺寸从 `imageManifest` 的 w/h 推算
- **dt 归一化**：惯性衰减按实际帧间隔归一，60/120/144 Hz 手感一致

### 状态变更必须调 scheduleUpdate()

这是**踩过的坑**：`setHover()` 只改状态不驱动渲染，因为悬停判定发生在渲染循环内部。
（当时）全项目 11 处状态变更都调了 `scheduleUpdate()`，唯独 `onHoverMove`/`onHoverOut` 漏了，
导致悬停放大完全失效。**新增任何状态变更都要记得调。**

## 转场：ptr 擦除覆盖层（src/components/PtrTransition.vue）

### 为什么用覆盖层而不是 View Transitions

曾经实现过 `document.startViewTransition` 的 3D 立方体版本，但参考站实际用的是
**自己实现的覆盖层**（代号 ptr）。已删除 VT 版（`src/core/pageTransition.js`）。

### 三段斜向擦除

三层 `.ptr-wipe-a` / `-b` / `-main`，每层内是 `skewX(-10deg)` 的填充块。
- 擦入（cover）：延迟 a=0s / b=0.06s / main=0.12s
- 擦出（reveal）：顺序反转 main=0s / b=0.06s / a=0.12s
- 时长 `.28s cubic-bezier(.7,0,.2,1)`
- `--ptr-x` 按方向注入：next=1（右侧进）、prev=-1（左侧进）

### 状态机

`null` → `{dir, phase:'cover'}` → `'reveal'` → `'idle'` → `null`

- **route push 发生在 toReveal() 内、phase 切到 reveal 之前** ——
  即「擦入盖住 → 切路由 → 擦出揭示新页面」
- 动画事件驱动：`ptr-wipe-in` 的 animationend 触发 toReveal，`ptr-wipe-out` 触发 finish
- **覆盖层必须常驻挂载（不能加 v-if）** —— 转场第一步是擦入盖住，
  按需挂载会先闪一帧旧页面

### 关键时序修正（我方优于参考站的地方）

参考站用 `Promise.all([就绪信号(1500), minCover(440)])`，由 1500ms 决定，
（注：参考站那个 helper 看着像字体等待，**其实不是**，所以 PtrTransition.vue 里刻意不叫 `waitForFonts`，别按那个名字去「修」它）
导致擦入结束到擦出之间**空等约 1483ms**，总时长 2.47s。

我方改为 `Promise.race([readySignal, pushReady])` 与 `minCover(440)` 竞速：
- 空等降到 **420~470ms**
- 总时长 **1.35s**（省约 1.1s）
- 必须保留 440ms 最短覆盖，否则覆盖层没铺满就擦出会露旧页面

### 方向判定

`ROUTE_ORDER = ['/', '/wall', '/cinema', '/pictorial']`
不在表内或起止相同 → 回退 `'next'`（**不是跳过动画**）。

## 影院页（src/views/Cinema.vue）

斜向照片流 + 上下霓虹跑马灯。**20 张照片 = 20 张卡，零重复**（用户 m04982 要求）。
- `.cinema-tilted { transform: rotate(-10deg) scale(1.1) }`
- 列方向交替：1/3/5 向下、2/4/6 向上
- 每列时长 55/62/50/68/58/64/52 秒（最多 6 列，第 7 个值 52 是预留）
- 无缝循环靠 `translateY(-50%)`，因此每列内容必须复制一份（副本打 `duplicate` 标记，`alt=''` + `aria-hidden`）

### 列分配：轮转法（不是步长公式）

`第 i 张照片 → 第 (i % count) 列`。天然零重复，相邻列永不共享同一张照片，
不需要「步长与池大小互质」这类数论约束（旧实现的 `gcd` 检查已删除）。

### 列数：几何实测自适应，不是固定断点

`COLUMN_MAX = 6`、`COLUMN_MIN = 2`。挂载后 `applyColumnCount()` 先按宽度给候选
（`>=1024`→6，`>=640`→5，其余 4），再用 `isColumnCountSafe()` 读真实布局验证
「每列最少张数 >= `ceil(列高 / 单卡步长)`」，不成立就减一列再测，最多试到 2。

**为什么不能只按宽度分档**：可见张数取决于**列高**（窗口高度）。
实测 1440x1200 时 6 列每列只有 3 张，但屏幕能放 4 张 —— 副本必然进视口。
1080x1920 竖屏更极端（每列 3 张、可见 8 张），会自动降到 4 列。

### 为什么桌面是 6 列而不是 7 列

20 张分 7 列 = `3,3,3,3,3,3,2`，末列 2 张 < 桌面可见 3 张，副本会进视口。
**「7 列」与「零重复」数学上不可兼得**。6 列得 `4,4,3,3,3,3`，最少 3 张刚好够。

### 两个容易踩的点

- `.cinema-cols` 必须绑 `:key="columnCount"`：列数变化时若不强制重建，
  `translateY(-50%)` 百分比会按新高度立即重算，画面瞬间平移一两张卡。
  重建是安全的 —— `-50%` 恰等于第二份内容的起点，与当前画面视觉等价。
- `--cinema-gap` 三档必须与列数断点一一对应，否则 `min-width` 与 `max-width`
  会互相覆盖（历史上 `768~1023` 区间的 10px 从未生效过）。

## 画报页（src/views/Pictorial.vue）

瀑布流卡片，复刻参考站首页。
- 列分配：贪心平衡（逐张放入累计高度最短的列）
- 挂载后 `measureHeights()` 用 `offsetHeight` 实测纠正估算
- 滚动入场用 `IntersectionObserver`（`rootMargin: '240px 0px'`）
- 断点：`>=1024` → 5 列，`>640` → 3 列，否则 2 列

### 3D 倾斜视差（逐字复刻参考站）

悬停时 6 个自定义属性，系数与参考站完全一致：

| 属性 | 公式 | 上限 |
|---|---|---|
| `--tilt-x` | `-(2*r*6)` | ±6deg |
| `--tilt-y` | `(2*n*8)` | ±8deg |
| `--card-par-x` | `(2*n*10)` | ±10px |
| `--card-par-y` | `(2*r*6)` | ±6px |
| `--tilt-shadow-x/y` | `-(2*n*12)` / `-(2*r*12)` | ±12px |

`n = clamp((x-cx)/w, -0.5, 0.5)`，`r = clamp((y-cy)/h, -0.5, 0.5)`

- 只在 `(hover: hover) and (pointer: fine)` 且非 reduced-motion 下启用，**setup 时算一次**
- 指针进入只量一次矩形，移动过程不读布局，写样式用 rAF 合并
- 过渡：静止 `0.45s cubic-bezier(.23,1,.32,1)`，倾斜中 `0.12s ease-out`

### 卡片头像 → 照片预览弹层（2026-10-20 新增）

点头像弹出「这张卡对应的照片」大图。**参考站形态照搬、内容与本项目适配。**

| 项 | 值 | 来源 |
|---|---|---|
| 弹层宽 / 圆角 | **卡片实宽**（随列数变化）/ 16px | 本项目决策（2026-10-26） |
| 背景 / 边框 | `rgba(20,20,28,.55)` / `1px solid rgba(255,255,255,.15)` | 参考站实测 |
| 阴影 / 模糊 | `0 24px 64px rgba(0,0,0,.5)` / `blur(24px) saturate(1.5)` | 参考站实测 |
| 默认位置 | 锚点下方、左对齐（`data-side=bottom` / `data-align=start`），间距 22px | 参考站实测 |
| 动画 | 200ms，`opacity 0→1` + `scale .95→1` + `translateY(-8px→0)` | 参考站实测 |
| 图片 | `assetUrl(entry.full)`（1600px 大图，**不是** thumb） | 本项目 |
| 叠层文字 | `NO.xx` + `美琴 · 画报`，不伪造点赞数 | 本项目 |

> ⚠️ **宽度口径已变（2026-10-26）**：参考站是固定 288px，本项目改为**跟卡片同宽**。
> 用户要求「悬停出现的宽度和它的父页面一致」，已确认取「卡片列宽」而不是整页宽。
> 高度**完全自适应**（= 宽度 / 宽高比），不再有 `max-height` 与 `hMax` 预算。

**定位算法**（`computePopoverPosition`）：
- 宽度 = 卡片实宽（`resolvePopoverWidth()` → `card.cardW`，由 `recordCardWidth()` 在渲染后写入）。
  **必须用 `clientWidth`**：卡片悬停带 `scale(1.05)`，`getBoundingClientRect().width` 会量成 276（真实 262）。
- 高度 = 照片区高度（宽度 / `fw/h`）+ 52px 信息条 + 2px 边框，**不设上限**。
- 翻转：下方放不下且上方更宽裕 → `side=top`（动画也随之改成从下往上）。
- 纵向**不钳制**（浮层随锚点逐像素移动）；横向 clamp 进视口（margin 12px），
  水平被挤走时 `align` 标成 `center`。
- 桌面顶部预留 90px（NavBar top20+高60+10），窄屏 88px —— 只用于翻转判定，不是钳制下界。

**锚点跟随**（`followAnchorFrame`）：打开浮层时卡片正处于悬停抬升动画
（`translateY(-10px) scale(1.05)`，以卡片中心为原点），头像还会继续移动约 5.5px。
打开后逐帧比对锚点 rect，只更新**基准**（`anchorBaseTop` 与 `anchorBaseAnchorTop` 一起走），
位置一律由基准公式算出；连续 40 帧静止后自停。
**不加这一层，间距会在 20~25px 之间随机漂移。**

**滚动跟随的基准必须是锚点 rect，不能是 `scrollTop` 增量**：
`scrollTop` 滚了 6px 不代表锚点在视口里也移动 6px（实测 394.02→388.72 只动了 5.3），
用 `scrollTop` 做基准则间距会累积漂开（实测 22→15）。
公式是 `round(anchorBaseTop + (r.top − anchorBaseAnchorTop))`，符号为**加**（写成减会让浮层反向跑）。
`handleScrollChange` 必须**同步**调用 `applyScrollShift`，不能排 rAF —— 排了就会出现
「浮层晚半拍」（实测滚动第一帧间距 22→26）。详见 `记忆/04` 第十二批。

**事件与清理**：`document click`(捕获) + `document keydown` + `window scroll`(捕获) + `window resize`
全部是**具名函数引用**，`detachGlobalListeners()` 幂等（`listenersBound` 标志），
关闭时与 `onUnmounted` 都会调用；关闭用 200ms 出场动画 + `setTimeout` 兜底（reduced-motion 时为 0ms）。

**两个必须知道的坑**：
1. **scoped 对 Teleport 生效**：Vue 3 会给 Teleport 出去的内容打 scope id（实测产物是
   `.card-popover[data-v-fbff2aa0]`），所以弹层样式可以写在 `<style scoped>` 里，不用全局样式。
   但 `@keyframes` 名**仍会**被 scoped 改写加 hash 后缀（实测 `cardPopoverIn-fbff2aa0`），前缀照旧要加。
2. **document 捕获监听的顺序**：跟在头像上的 `@click.stop` 之前触发，所以
   `handleDocClick` 必须自己 `closest('.card-avatar')` 排除头像，不能只靠 stopPropagation。

**为什么头像包 `<button>` 而不是给 `<img>` 加 tabindex**：原生键盘可达 + Enter/Space
无需手写；`.card-avatar` 宽度固定 2.5rem、`display:block`，卡片总高不变（不影响贪心分配）。

## 画报页卡面高度：按照片真实比例（2026-10-23 决策）

**规则**：`.card-media` 的高度由每张照片**自己在清单里的 w/h** 决定，不再用固定比例。

- 模板内联：`:style="{ aspectRatio: card.w + ' / ' + card.h }"`。必须内联，不能只写 CSS ——
  图片是 `position: absolute; inset: 0` 不参与布局，容器高度只能靠 `aspect-ratio` 预留，
  而 CSS 里拿不到每张卡的 w/h。
- CSS 兜底：`aspect-ratio: 3 / 4`，与 JS 里的 `0.75` 同源，**只在清单条目缺 w/h 时生效**。改一处必须改另一处。
- **不要改回固定值**：固定值会让 23 张卡等高，整页失去瀑布流的参差感（这就是曾经的问题）。

**为什么参考站看起来更「有个性」**：它的图片区本来就不是正方形（实测 260x171，约 1.52 横构图），
且每张图按自己比例出高度。本项目清单共 7 种比例（0.5625 ~ 1.772，极差 3.15 倍）。

**列宽取值**：`assignColumns` 必须取 `.card-shell` 的 `clientWidth`（卡片实宽），
**不能**取 `.masonry-column` 的 —— 后者含 `padding-left`，桌面 5 列时是 278 而卡片实宽只有 262，
高估约 6%，且误差随 `1/ratio` 放大，与「竖图更高」的方向叠加。

**`measured` 缓存**：`uid -> px`，不含列宽维度。列数变化时必须 `clear()`。

**`rebuild()` 的微任务契约**：函数体内两处 `await nextTick()` **必须在微任务内结算**。
浏览器不在微任务排空前绘制，所以「先估算分配、再实测纠正」的中间态不会上屏。
**不要**改成 `await new Promise(r => requestAnimationFrame(r))` —— 中间态会真的渲染出来，变成整列跳动。
## 画报页列数断点：7 档查表（2026-10-23 决策）

**规则**：列数由 `COLUMN_BREAKPOINTS` 查表决定，**不要写成线性公式**。

| minWidth | cols |
|---|---|
| 1900 | 8 |
| 1680 | 7 |
| 1500 | 6 |
| 1280 | 5 |
| 1024 | 4 |
| 768 | 3 |
| <768 | 2 |

**为什么查表**：档位间隔不均匀（768→1024 = 256、1024→1280 = 256、1280→1500 = 220、
1500→1680 = 180、1680→1900 = 220）。曾经用 `3 + floor((w-768)/256)` 的线性式，
它假设每档递增 256，导致 1500 / 1680 / 1900 三个分界点全部推迟 1px 才生效。
档位是实测值，不是可解析级数。

**间距常量动不得**：`.masonry-grid { margin-left: -16px }` + `.masonry-column { padding-left: 16px }`
（≤640px 时都是 8px），卡片间实际间距恒为 16px，与参考站一致。**列数变了不需要动这两个值。**

**列数变更的连带影响**：列数变 → 列宽变 → `measured` 缓存（`uid -> px`，不含列宽维度）失效，
`onResize` 里必须 `measured.clear()`（已有逻辑，改断点表不影响它，但改动时别删）。
