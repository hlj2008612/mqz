## 已验证但不算缺陷的现象

- **同一张图在照片墙出现 2 个实例**：`imageIndexAt` 让 300 槽位里每张图被 15 个槽位复用，

### 关键结论：为什么桌面是 6 列而不是 7 列

20 张照片分 7 列必然得到 `3,3,3,3,3,3,2`，末列只有 2 张，而桌面单屏可见 3 张 ——
那一列循环时副本会进入视口，**「7 列」与「零重复」在数学上不可兼得**。
分 6 列得到 `4,4,3,3,3,3`，最少 3 张，恰好够。

### 教训

**「按宽度分档」不足以保证「每列张数 >= 可见张数」** —— 可见张数 = `ceil(列高 / 单卡步长)`，
列高来自窗口高度。竖屏显示器（1080x1920）和未最大化的高窗口（1440x1200）都会翻车。
凡涉及「屏幕里能看到几个」的判断，必须读真实布局，不能只按宽度推断。

## 转场覆盖层吃掉点击事件

- **现象**：转场进行中快速点击另一个导航项没有反应，最终停在第一个点击的目标。
- **根因**：`src/assets/main.css` 里 `.ptr-root` 是 `pointer-events: auto`（照参考站原样抄的）。
  参考站覆盖层自带横滑手势翻页、必须接住触摸事件；我方没有手势，覆盖层纯视觉，
  保留 auto 会让转场期间所有点击落在覆盖层的装饰元素上，导航栏收不到任何事件。
  实测 `elementFromPoint(500,51)` 在 cover 阶段返回无类名 `SPAN`，`navHitSelf=false`。
- **修复**：`.ptr-root` 改为 `pointer-events: none`。空闲态原本就是 none，两种状态行为一致。
  同类问题还有键盘 Tab 焦点会被吸进覆盖层的装饰元素里，一并解决。
- **另一处**：`PtrTransition.vue` 的 `reconcile()` 原先只做 `router.push`、从不播转场，
  导致挂起的第二次点击永远等不到补播。现在 busy 时交回 `drainPending()`，busy 已释放则 `start()` 补播。
- **验证**（真 Chrome 1440x900，3 种连点节奏）：修复前全部只播 1 轮、停在 `#/cinema`；
  修复后 280ms/60ms 间隔均为 2 轮、落在 `#/pictorial`，连点 5 项为 2 轮、落在 `#/wall`。

## 转场时导航栏压在覆盖层上面

- **根因**：`.glass-nav` 是 `position: fixed` + `z-index: 99999`（`NavBar.vue:137` 写死），
  `.ptr-root` 只有 20000，且两者都在 body 下（ptr 经 Teleport）。
- **修复**：转场期间在 `<html>` 打 `data-ptr-active`，`main.css` 里

  Pictorial 的 `.card-popover`(2000) 重新排优先级，且将来任何人写更大数字就会顶破。

## 画报页头像资料卡：指针穿不过空隙导致弹层提前关闭

- **现象**：鼠标从头像移向资料卡时，弹层在中途消失，用户点不到里面的「查看大图」。
- **根因**：头像与弹层之间有 `POPOVER_GAP = 22px` 的空隙（`Pictorial.vue`）。指针经过这段空隙时
  命中的是卡片背景，先触发头像的 `mouseleave`，220ms 倒计时到点就关闭。
  真机实测：16px 间隙、3 次 `mouse.move` 后弹层在 `y=480` 就消失（弹层从 `y=484` 才开始）。
- **修复**：`maybeCloseByPointer()`——关闭定时器到点时不再无条件关闭，而是用真实指针坐标再判一次：
  指针在「弹层矩形」或「头像矩形」内（各 8px 容差）就不关；夹在两者之间视为还在穿越空隙，
  重新排一个 220ms 定时器继续观察。指针位置由 `window` 上的 `mousemove(trackPointer, passive)` 记录。
- **踩坑**：一开始想用 `.card-popover::before` 加透明桥接区盖住空隙，但 `.card-popover` 有
  `overflow: hidden`，负 inset 的伪元素会被裁掉，方案不可行（已撤回）。

## 画报页资料卡：三个由专家审查发现的问题

1. **指针未知时按 (0,0) 判定**（`pointerKnown` 守卫）：`lastPointerX/Y` 初值是 0，
   而 `inRect` 有 8px 容差，于是「从未移动过指针」时视口左上角 `(-8..8)` 会被误判成「还在头像里」，
   弹层永远关不掉。触屏（只 tap 不 move）和纯键盘操作会踩到。修：未知位置 = 按已离开处理。
2. **指针静止在空隙里会无限重排定时器**：只按「还在空隙里」重排的话，指针停在缝隙中不动时
   定时器永远每 220ms 重排一次。真机实测静止 3 秒创建 **14 次**，每次还读两次 `getBoundingClientRect()`。
   修：`closeProbeCount` 上限 `CLOSE_PROBE_MAX = 5`，加上首次判定共 6 次 ≈ 1.4 秒，超限强制关闭。
   验证据此校准：验收专家实测 6 次、Lead 从指针入空隙起计数得 5 次（起点不同），均约 1.4 秒后关闭。
3. **弹层固定高 320 与实测 339 差 19px**：`computePopoverPosition` 的
   `spaceBelow/spaceAbove` 判断会失真，判定「下方放得下」但实际渲染底部被视口裁掉，
   最下面的「查看大图」按钮点不到。修：`popoverMeasuredHeight` 缓存 `nextTick` 里测到的
   `el.offsetHeight`（实测 339），常量也同步改为 339。
   【注意】必须用 `offsetHeight` 而不是 `getBoundingClientRect().height`：入场动画从 `scale(0.95)` 起步，
   nextTick 那一刻 rect 只有 322 而布局高度已是 339，用 rect 会把高度永久记小 17px。

## 教训：用 splice 搬移代码块会留下注释残骸

搬移「声明 + 前置注释」时，回溯找注释起点的循环只认 `/**`，结果切掉了注释开头却把中间几行
留在原处，产生孤立的 ` * 首次渲染后测到的真实高度。` 这种行，构建直接报
`SyntaxError: [vue/compiler-sfc] Unexpected token`。
**做法**：搬移后必须用 `node --check` 单独校验 `<script>` 段，不要直接跑 `npm run build` 等它报错。

## 专家报了但**不采纳**的一条（记录理由，防止以后重复讨论）

审查建议「`maybeCloseByPointer` 第一/第二分支（指针在弹层或头像矩形内）也要加计数上限，超限强制关闭」。**不采纳**。
理由：`maybeCloseByPointer` 只在 `hoverCloseTimer` 到期（指针已离开头像）后调用，语义是
「220ms 后指针在哪」。指针落在弹层内 = 用户正移进弹层操作，此时关闭才是缺陷。
加了上限会让「鼠标停在资料卡上读内容超过 1.4 秒」被强制关闭。

已实测确认的现象：**指针停在弹层内不动、只滚动页面，弹层保持打开**（滚动 400px 与 800px 后均为 1）。
这是**预期行为**不是缺陷 —— `handleViewportChange` -> `positionPopover` 会让弹层跟着锚点重新定位
（实测弹层 y 始终 485 贴着头像），视觉上弹层一直在照片旁边，此时关闭反而突兀。
唯一理论边界：指针黏在视口固定位置、内容滚走很远后弹层因跟随锚点而离开该点，判定会改成关闭；
实测两次滚动均未触发，属可接受的边界。

顺带修掉的三个定位问题：

1. **边框没算进去**。弹层是 `box-sizing: border-box`，照片实际可用宽是 318 而不是 320；

   弹层贴底时会先按下方位、再由 nextTick 实测改判，产生一次 2px 可见抖动。

3. **窄屏 CSS 与脚本公式不一致**。脚本是 `min(320, 视口-24)`，CSS 原本只写死 320px。

实测四档视口（1440x900 / 768x1024 / 344x800 / 320x700）：弹层均无左右溢出、无上下溢出、页面错误 0。

## 2026-10-20 第 27 轮：悬停浮层入场动画对齐 + Esc 与导航遮挡修复

### 参考站入场动画的真实机制（真 Chrome 实测，权威）

浮层是 Radix HoverCard，**两层 DOM**：wrapper `[data-radix-popper-content-wrapper]` + 内容层（其 firstElementChild）。

- 动画声明在**内容层**：`animation-name: enter`、0.3s、`cubic-bezier(0.16, 1, 0.3, 1)`、`fill-mode: both`、`transform-origin: 0px 0px`
- 内容层自己的 transform 全程 none —— 缩放不发生在内容层
- 关键帧来自 tailwindcss-animate，**只定义 0% 一帧**，终点落到元素默认值：
  `@keyframes enter { 0% { opacity: var(--tw-enter-opacity,1); transform: translate3d(...,0) scale3d(...) } }`
- 实测变量：`--tw-enter-opacity: 0`、`--tw-enter-translate-y: -8px`、`--tw-enter-scale: 0.95`

按 `animation.currentTime` 对齐采样：t=0 op=0；t=67 op=0.788；t=133 op=0.957；t=200 op=0.994；t=267 op=1。
前约 1/3 时长视觉上几乎不可见。

**盒子底与 backdrop-filter 一起淡入**（用 `getAnimations()` 把动画 pause 到 currentTime=67，
读内容层计算样式得 `{ op: 0.789718, bg: rgba(20,20,28,0.55), bfi: blur(24px) saturate(1.5) }`）。

### 采样失败的三种方式（勿重试）

1. wrapper 的 `getBoundingClientRect()` 宽高恒为 288x384（transform 不改变其 width/height），只能用 `cs.transform` / `cs.opacity`；
2. `document.querySelector('[data-state=open]')` 会命中页面上**别的高亮元素**（272.1x42.6、transform none），页面里有多个；
3. 局部 rAF 循环会在 700ms 后自行停掉、拿不到首帧。**要采首帧必须先把循环注册好，再 `page.mouse.move`**。

### 我方落地的改动（src/views/Pictorial.vue）

| 项目 | 改前 | 改后 |
| --- | --- | --- |
| `transform-origin` | `50% 50%` | `0 0`（`[data-side=top]` 为 `0 100%`） |
| `will-change` | 常驻 `transform, opacity` | 只在 `.is-open` / `.is-closing` 声明 |
| 入场动画 | 200ms cubic-bezier(.23,1,.32,1) | 300ms cubic-bezier(.16,1,.3,1)，scale .95→1 + translateY(-8px)→0 |

**为什么 origin 是 0 0**：我方没有 popper wrapper，`top`/`left` 直接落在锚点旁，
左上角天然就是「靠近锚点的角」，缩放必须从这里长出来才与参考站观感一致。

实测（1440x900）：t=0 op=0 sc=0.95 ty=-8 origin=0px 0px；t=50 op=0.686 sc=0.9843；
t=117 op=0.935 sc=0.9967；t=183 op=0.989 sc=0.9995；t=267 op=1 sc=1。曲线与参考站一致。

### 缺陷：Esc 关不掉悬停弹层

**现象**：悬停打开弹层后按 Esc，弹层不关（normal 与 reduce 两种模式都复现）。

**排查过程**（两次误判，记下来避免重走）：

1. 先怀疑「捕获阶段收不到 keydown」→ 改成 `capture: true`，无效；
2. 加页面内探针证明 `handleDocKeydown` **确实执行了**（`handler:Escape active=true bound=true`），
   但 `pop` 仍为 1 —— 说明关闭后**又被重新打开**；
3. 给 `openPreview` 插桩记录调用栈，确认重开来自 `onAvatarEnter` 的 `hoverOpenTimer` 延迟回调。

**根因**：Esc 关闭后指针仍停在头像上，`onAvatarEnter` 的 255ms 延迟打开把弹层又弹了回来。

**修复**：新增 `escSuppressedAnchor`，记录「被抑制的那个头像」（不是全局布尔）：

- `handleDocKeydown`：`escSuppressedAnchor = hoverAnchorEl;` 然后 `closePreview();`
- `onAvatarEnter`：`if (escSuppressedAnchor && escSuppressedAnchor === anchor) return;`
- `onAvatarLeave`：`escSuppressedAnchor = null;` 解除

**为什么不用全局布尔**：全局布尔要靠「一定有某次 mouseleave 发生」来解除，
键盘用户 Esc 后直接 Tab 到下一张头像时，下一次 `onAvatarEnter` 先于解除执行，会白吞一次聚焦。
改成记录锚点后，别的头像照常弹出，**无需依赖任何离开事件即可自愈**。

**★ 顺序坑（本轮真踩过）**：`escSuppressedAnchor = hoverAnchorEl` 必须在 `closePreview()` **之前**。
`closePreview()` 的 reduce 分支会**同步**把 `hoverAnchorEl` 置 null，放在后面会记下 null，等于没抑制。
症状：Esc 后 100ms pop=0（关掉了），200ms 后 pop=1（又弹回来），normal 模式不明显因为 reduce 分支不执行。

### 缺陷：弹层向上翻时钻进导航栏

**现象**：1280x720 / 1366x768 下弹层翻到上方后被钳到 `y=12`，
被 `.glass-nav`（`top:20 + height:60`，底边 82，`z-index:99999`）压在下面。
复现证据：`elementsFromPoint(60,45)` = `['glass-nav','IMG','card-popover-photo']`。

**修复**：新增 `NAV_SAFE_TOP = 90` / `NAV_SAFE_TOP_NARROW = 88`，
`computePopoverPosition` 里 `spaceAbove` 与竖向 clamp 下界都用 `safeTop` 而非 `POPOVER_MARGIN(12)`。

**数值依据**：桌面导航 `top:20 + height:60` = 底边 80，取 90 留 10px；
窄屏 `height:54` 底边 74，取 88 留 14px。断点 `vw <= 640` 与 NavBar 的媒体查询同侧。
**这两个常量与 `NavBar.vue` 的导航高度联动**，改那边记得改这里。

验证：1280x720 与 1366x768 的 `y` 由 12 变 **90**，`overlapNav` 由 true 变 **false**。
1440x900 仍是 `side=bottom`、`y=358`，不受影响。

**已知限制**：`vh < 约 580px` 时底部信息条可能被裁到视口外，属 `NAV_SAFE_TOP` 的必然代价

## 2026-10-21 导航栏滚动收起 / 展开（规格 docs/nav-scroll-and-popover-spec.md 第一节）

**已实测（真 Chrome 无头 1440x900，`npx vite preview` + playwright-core，构建产物）**：

| 操作 | 实测结果 |
|---|---|
| 向下累计 1 / 50 / 99px | 不动，top 恒为 20（底边 82） |
| 向下累计 100px | 收起，top=-79、bottom=-17，`is-hidden=true`，transform=matrix(...,-625,-99) |
| 向下累计 200px | 保持收起 |
| 收起后向上 1 / 2 / 5 / 7px | 仍收起 |
| 收起后向上累计 10px | 展开，top 回到 20 |
| 回顶（scrollTop=0） | 强制展开 |
| 375px 视口 | 收起后 top=-74、bottom=-20（完全移出），left=8 居中未坏 |
| reduced-motion | transition-duration 实测 1e-05s（全局规则生效），收起/展开仍瞬时生效、不卡死 |

**实现要点**：`transform: translateX(-50%) translateY(var(--nav-hide-y))` 同一条 transform（不能内联覆盖，否则丢居中）；
`--nav-hide-y` 桌面 -99px、`max-width:767px` 覆盖为 -94px；transition `transform .3s cubic-bezier(.4,0,.2,1)`；
阈值 `HIDE_DOWN=100` / `SHOW_UP=10`，方向反转即清零累计；rAF 节流；`document.hidden` 时同步补算（后台 rAF 会被暂停）；
`data-ptr-active` 期间跳过；卸载时移除 scroll 监听 + cancelAnimationFrame。

**坑 1（本轮踩到）**：本站 `html/body/#app` 全被钉成 `overflow:hidden`，**window 永远不滚动**；
① 真实滚动容器是 `.pictorial-page`（overflow-y:auto），scroll 事件不冒泡，必须 `window.addEventListener('scroll', h, {capture:true})` 才能收到；
② 阈值必须累加 `e.target.scrollTop` —— 只读 `window.scrollY` 永远不会触发。

**坑 2（已知、未修）**：`.pictorial-page` 被销毁后重建时 scrollTop 归 0（浏览器不会给非 window 容器恢复位置），
但 `<router-view>` 未包 KeepAlive，Vue 仍把同一元素上的 class 变更打补丁 —— 实测「收起后跳到影院再回画报」时
scrollTop=0 却仍是 `is-hidden`，导航栏留在屏外。影院/首页当前不可滚动（scrollH=clientH），实际触发路径窄，
记录为已知限制；彻底修需在 NavBar 里加「滚动容器被替换时重新校准」的兜底。

## 2026-10-21 悬停浮层不跟滚动走（被钳在视口里不动）

- **现象**：悬停头像（y=428）打开浮层（高 530，top=358），把 `.pictorial-page.scrollTop` 设为 100 后
  头像变 y=328 而浮层 top 仍是 358，完全不动；手动 `window.dispatchEvent(new Event('scroll'))` 也不动。
- **根因**：`src/views/Pictorial.vue` 的 `computePopoverPosition()` 把纵向 top 钳进视口：
  `top = clampNum(top, safeTop, max(safeTop, vh - POPOVER_MARGIN - size.height))`，
  上界 = 900-12-530 = 358。滚动后 below = 328+40+22 = 390 > 358 被压回 358；
  滚动前后都落在同一上界，所以「看起来没动」。
- **参考站实测（同浏览器 forum.hanakos.cc）**：浮层与锚点逐像素同步，允许底部出视口：
  锚点 248→浮层 308、181→235、106→157、26→77（每次位移都等于锚点位移）。
- **修复**：纵向不再钳制，改为贴边公式
  `top = side === 'bottom' ? rect.bottom + POPOVER_GAP : rect.top - POPOVER_GAP - size.height`；
  **翻转判定完全保留**（`size.height > spaceBelow` 且 `spaceAbove > spaceBelow` 时翻成 top），
  `NAV_SAFE_TOP` 只留在 `spaceAbove` 里做判定、不再当钳制下界；**横向 clamp 保留**。
  相关注释共约 9 处按新语义重写。
- **边界策略：不因「浮层完全滚出视口」而关闭浮层**。理由：① bottom 侧浮层要等锚点顶端越过视口上边
  22+530=552px 才会完全出屏，那时卡片早已整张滚出、指针也离开卡片走既有关闭逻辑，「孤儿浮层」几乎不可达；
  ② 新增「矩形与视口无交集就关闭」会在 `getBoundingClientRect()` 抖动时误关（transform 动画/虚拟滚动期间都可能），
  引入新的关闭竞态；③ 参考站同样是「跟着锚点走、允许被裁」。
- **实测（真 Chrome 无头 1440x900，`npx vite preview` 指向本项目 dist，playwright-core）**：
  滚 scrollTop 0/100/200/300 时浮层 style.top 486→390→290→190，每段位移 96/100/100px，与锚点位移逐像素一致
  （差值恒 2.36px，来自 `.card-tilt` 3D 透视带来的亚像素高度 41.7↔40，浮层按整数 96 落位，不是错误）；
  翻转分支 `side=top` 时 top 136→45（锚点 -91.7、浮层 -91.0）；滚到 400 时锚点 y=28.39、浮层 top=90。
  截图逐像素核对（锚点红框 / 浮层青框）：浮层顶边框 481→381→287→187，锚点顶边框 418→326→226→126，每步 -100。

**坑（本轮踩到）**：headless Chrome 读锚点 `getBoundingClientRect()`，**滚回 scrollTop=0 的那一拍**会拿到
带 `.card-tilt` 透视的 41.7px 高旧值（静止 40px），该点差值额外偏 1.7px，再滚一次即恢复；
判断「浮层跟没跟」要看 style.top 的**连续位移量**，不要只看单点 gap。

1. 先测了参考站的**用户信息浮层**（`.user-card-banner`）和我们**照片墙 /wall** 的悬停，
   都不是用户说的对象。用户说的是**画报页 /pictorial**。定位视觉问题前必须先确认页面。
2. 用 `window.scrollY` 测画报页滚动恒为 0 —— 画报页的滚动容器是 `.pictorial-page`，

1. **cpp/⌘ 手势直接 return，不能 preventDefault**：实测 ctrl+wheel 时 `ctrlKey` 为 true，

## 第五批：浮层滚动跟随时每帧强制布局（2026-10-22，真 GPU 实测）

**症状**：画报页悬停头像弹出浮层后滚动页面，弹层总比页面「慢半拍」，手感发涩。

**根因（与参考站的机制差异）**：参考站浮层是**两层结构** —— 外层包裹节点
`position: fixed; top: 0; left: 0`，位置**完全由内联 `transform: translate(x, y)` 逐帧承担**
（实测滚动前后 `translate(29px, 328px)` → `translate(33px, 215px)`，`top`/`left` 恒为 `0px`）；
内层才是视觉卡片（`background: rgba(20,20,28,0.55)`、`backdrop-filter: blur(24px) saturate(1.5)`、
`border-radius: 16px`、`border: 1px solid rgba(255,255,255,0.15)`、`overflow: hidden`）。
我方原先**一个元素同时承担定位与视觉**，且逐帧写 `el.style.top` / `el.style.left` ——
这两个是**布局属性**，每帧触发一次布局；叠加 `backdrop-filter` 后布局变化
还会让模糊背景重新采样，于是弹层永远追不上页面。

**修法**：位置改由**独立的 `translate` 属性**承担（合成层属性，不参与布局）：

- CSS `.card-popover` 加 `top: 0; left: 0;`
- 新增 `supportsTranslateProp()`（探测 `CSS.supports('translate','1px 1px')`）与**唯一写入入口**
  `writePopoverOffset(el, top, left)`，内部写 `` `${left}px ${top}px` ``
- `applyScrollShift()`、`syncPopoverDom()`、`onUpdated()` 三处全部收敛到该入口
- **不能改用 `transform`**：它已被入场/出场的 keyframes（`scale` + `translateY`）占用；
  `translate` 与 `transform` 是不同的 CSS 属性，可并存且互不覆盖
- 无 `translate` 支持时回退写 `top`/`left`（用 `addInitScript` 覆盖 `CSS.supports` 已实测该通路）

**实测收益**（浮层开启 + 24 格 × 40px 滚轮，CDP `Performance.getMetrics`）：
```
改前  LayoutCount 10  RecalcStyleDuration 0.040s  ScriptDuration 0.017s
改后  LayoutCount  3  RecalcStyleDuration 0.010s  ScriptDuration 0.010s
```
`LayoutCount` 3 已与「冻结跟随写入」的下限持平 = 滚动热路径上的布局开销清零。

**易错点（代码审查工程师指出）**：

1. `el.style.translate` 读回来的值是**被 CSS 序列化过的**：`'46px 0px'` → `'46px'`、
   `'0px 0px'` → `'0px'`。所以「不相等才写」在 y=0 时判断恒真、反而每次都写。
   已改为**无条件写**（patch 是低频事件，同值赋值代价近乎为零）。
2. **参数顺序与属性顺序相反**：函数签名是 `(top, left)`，CSS `translate` 是 `x y`，
   内部必须写 `` `${left}px ${top}px` ``。写错会让位移互换但仍「看起来在动」，极难排查。
3. `transform-origin` 不受影响：纯平移项与原点互相抵消（带原点矩阵为 `T(o)·M·T(-o)`），
   且规范复合顺序是 `translate → rotate → scale → transform`，keyframes 的 `scale` 落在最后的 `transform` 上。

**验证**（真 Chrome 155，0 JS 错误）：

- 位置一致：`translate 46px 358px` == `rect (46, 358)`，`getComputedStyle` 的 `top`/`left` 恒为 `0px`
- 滚动 120px → 浮层位移 -120 精确
- 开合序列 `is-open → is-closing → gone` 正常，`border-radius` 16px、`backdrop-filter` 均保留
- 强制回退路径：桌面 = `top:358px left:46px`、位移 -120 ✓；
  390×844 窄屏 = `top:298px left:12px`、`rect (12,298)` ✓（窄屏位移为 0 是既有设计，非回归）

## 第六批：浮层永不关闭与窄屏覆盖锚点（2026-10-23，真 Chrome 实测）

**症状**：画报页浮层打开后滚到底也关不掉；手机端浮层盖住头像、Esc 后自动弹回。

### 6.1 钳制方案在数学上无解（先证伪，再改设计）

原方案是「把浮层钳进视口，同时保证不覆盖锚点」。实测证明**两者可能同时不成立**：

> clamp 被触发 ⟺ 视口内不存在既不覆盖锚点、又完整可见的合法位置。
>
> 设浮层自然高度 H、锚点上方可用 spaceAbove、下方 spaceBelow。
> 不覆盖锚点的合法位置集合是 (-∞, anchorTop-H] ∪ [anchorBottom, +∞)，
> 再与视口 [safeTop, vh-margin-H] 求交。当 H > spaceAbove 且 H > spaceBelow 时，两段解集都为空。
> 实测 1440x900 命中：H=530、spaceBelow=398、spaceAbove=316 ⇒ 无解。

**修法**：不再试图同时满足，改为**让浮层高度服从预算**：
`H := min(自然高度, (vh - 186) / 2)`，其中 186 = 上下安全边距 + 锚点高度。
高度压到「无论浮层落在锚点上方还是下方，都一定放得下」的量级，于是
「不覆盖锚点」与「完整可见」重新相容，clamp 不再需要。

### 6.2 窄屏不跟随滚动，导致锚点撞进浮层（真实缺陷）

`applyScrollShift()` 里原有 `const vwNow = ...window.innerWidth; if (vwNow <= 640) return;`。

**反证一（源站行为）**：390x844 iPhone UA 实测，点击后浮层 top=273，
滚 60px → 213、滚 120px → 93、滚 200px → **-107**。位移恒等于滚动量，
窄屏同样精确跟随，且允许浮层滚出视口顶部**不做钳制**。

**反证二（不变量被破坏）**：浮层钉死在打开位置、锚点随页面走，两者必然相交。
实测 390x844 先滚 400 再点开、然后向上滚：浮层钉死 503 不动，锚点 441→491→591→741，
滚 -50/-100/-150px 时「不重叠 = false」，直到 -200px 才分开。
锚点被浮层盖住后指针落在浮层内部 ⇒ 关闭链失效 ⇒ 又一个永不关闭。

**修法**：删除这两行，窄屏与桌面共用同一套逐像素平移。

## 第七批：画报卡面全部等高，整页像表格（2026-10-23，实测）

**现象**：画报页 23 张卡全部等高 373px，纵向看是一条条横线，用户评价「看起来像表格不像瀑布流」。

**根因**：`src/views/Pictorial.vue` 的 `.card-media` 写死 `aspect-ratio: 1 / 1`。
参考站并非正方形 —— 实测 `.image-glow.card-view-image` 是 260x171（约 1.52 的横构图），
而且每张图按自己清单里的 w/h 出高度，卡片高 195~725px 参差。

**修复**：

| # | 位置 | 改法 |
|---|---|---|
| 1 | 模板 `.card-media` | 内联 `:style="{ aspectRatio: card.w + ' / ' + card.h }"`，图片进 DOM 前容器就占好高度，不会加载后跳一下 |
| 2 | CSS `.card-media` | `aspect-ratio: 3 / 4`，只在清单条目缺 w/h 时兜底 |
| 3 | `estimateHeight(columnWidth, card)` | 新增 card 参数，按 w/h 估算图片高度 |
| 4 | `assignColumns` | fallback 改为逐卡估算 |

**为什么第 3 条必须改**：贪心分列用的是估算高度。若仍按常量估高，
16:9 横图会被当成 9:16 竖图一样高，分列结果与实际落差大，列高失衡。

**实测（真 Chrome）**：

| 视口 | 列数 | 卡片高 | 列高极差 |
|---|---|---|---|
| 1440x900 | 5 | 227~546 | 374 |
| 1024x768 | 5 | 180~398 | 285 |
| 390x844 | 2 | 178~390 | 318 |

三档均无横向溢出，0 页面错误。清单里共 7 种比例（0.5625 ~ 1.772，极差 3.15 倍）。

### 7.1 附带纠正一个长期误读：参考站并**不**平衡列高

`docs/pictorial-spec.md` 曾把「参考站 5 列盒子高度完全相等（2361px）」当成「它按高度平衡分配」的证据。**这是误读。**

- 参考站三档视口下所有 `.masonry-grid-column` 盒子高度确实完全相等（2361 / 2763 / 3932，极差 0），
  但那是父级 `.masonry-grid` 的 **flex 拉伸**把每列盒子撑到等高。
- 实测各列「最后一个子元素底边」= **2208 / 2345 / 2224 / 1707 / 2054**，内容底部极差 **638px**。
- 本项目同项极差 374px —— **比参考站更整齐**。
- 且贪心 + 局部搜索优化（试把任一列任一卡移到另一列以缩小极差）结果完全相同，
  说明贪心已处于局部最优，374~375px 极差是 23 张卡 / 5 列在数据分布下的下界，**不是缺陷**。

### 7.2 列宽取值的 6% 系统偏差

`assignColumns` 原来取 `.masonry-column` 的 `clientWidth`，它含 `padding-left: 1rem`（窄屏 0.5rem）。
桌面 5 列时列 clientWidth 是 278，而卡片实宽只有 **262**。

误差随 `1/ratio` 放大 —— 横图误差小、竖图误差大，**正好与「竖图更高」的方向叠加**，让高估更严重。
改为取 `.card-shell` 的 `clientWidth`。

### 7.3 跨断点 measured 缓存不失效

`measured` 是 `uid -> px`，**不含列宽维度**。列数一变列宽必然变，旧高度全部失效。
原实现靠随后的实测纠正，但那依赖 `rebuild()` 里两次 `await nextTick()` 都是微任务、中间态不上屏这个**隐式契约**。
改为在 `onResize` 里列数变化时先 `measured.clear()`，把失效数据挡在入口。

`rebuild()` 已补 JSDoc 显式写明该契约：**不要**改成 `await new Promise(r => requestAnimationFrame(r))`，
否则中间那次用估算值分配的列会真的渲染出来，变成肉眼可见的整列跳动。

**专家审查结论**：代码审查工程师判定**没有任何阻塞项**。
其中「card.w/h 缺失/0/负数会不会产生 Infinity/NaN」一项，依据是 `src/core/config.js:29` 的 `validatePool` 已要求 `w>0 && h>0`，
且 `src/views/Pictorial.vue:380` 的 `card && card.w > 0 && card.h > 0` 对 undefined/NaN/0/负数一律 false（`NaN > 0` 为 false）。

**提交**（均无 BOM）：`ec23a6b` 比例自适应、`9823fd1` 列宽取实宽 + 跨断点清缓存 + 规格同步。
## 第八批：画报页列数断点与参考站不一致（2026-10-23，真 Chrome 实测）

**用户反馈**：「我想要卡面上下左右之前的距离和源网站一样」。

**第一次实测的结论：间距本来就一致，不要改。**

| 项目 | 参考站 | 本项目 |
|---|---|---|
| 列内竖向间距 | 16px | 16px |
| 列间水平间距 | 16px | 16px |
| 列宽（1440） | 278.39 | 278.39 |
| 卡片宽（1440） | 262.39 | 262.39 |
| `.masonry-grid` | `margin-left: -16px` | 同 |
| `.masonry-column` | `padding-left: 16px` | 同 |

**测量陷阱（会让间距虚高 20px）**：`.card-shell` 的入场初始态是 `transform: translateY(20px)`，
未触发 IntersectionObserver 的卡片还没进入 `is-settled`，此时 `getBoundingClientRect()` 量到的间距是 36 而非 16。
必须先滚完整个页面让所有卡都拿到 `is-settled` 再测。**这与「第六批 6.4」记录的滚动容器陷阱是同一类错误：测量方法错会伪造出缺陷。**

|---|---|---|
| <768 | 2 | 2 |
| 768~1023 | 3 | 3 |

| 1280~1499 | 5 | 5 |
| 1500~1679 | **6** | **5** |
| 1680~1899 | **7** | **5** |
| ≥1900 | **8** | **5** |

### 8.1 一个「看起来很合理」的公式把三个分界点全推后了 1px

实测断点后先写成线性式 `3 + floor((w - 768) / 256)`，它假设每档递增 256。
但档位间隔**不均匀**：768→1024 = 256、1024→1280 = 256，而 1280→1500 = **220**、1500→1680 = **180**、1680→1900 = **220**。

实测后果：1500 出 5 列（应 6）、1680 出 6 列（应 7）、1900 出 7 列（应 8）—— 三个分界点全部**推迟 1px** 才生效。
这类错误在整百宽度的常规抽查里看不出来（1450 / 1600 / 1800 都对），只有正好踩在分界点上才暴露。
**档位是实测值、不是可解析级数，硬套公式必然错位 → 改为查表 `COLUMN_BREAKPOINTS`。**
